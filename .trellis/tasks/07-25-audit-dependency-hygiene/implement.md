2. **A-033 lock generation.**
   - Add to `Makefile`:
     ```
     # Regenerate the hash-locked dev requirements (requires uv + network).
     lock:
     	uv pip compile --universal --python-version 3.10 --generate-hashes \
     	  --no-header --only-binary :all: requirements-dev.txt -o requirements-dev.lock
     ```
     `--only-binary :all:` is not optional decoration: without it the resolver
     may build an sdist just to read its metadata, running the build hooks this
     task exists to close off. A 2026-08-10 probe confirmed the flag produces a
     byte-identical lock, so it costs nothing now.
   - Run `make lock`; commit `requirements-dev.lock`.
   - Expected content as of 2026-08-10: 10 entries — the 4 direct pins plus
     `ast-serialize`, `librt`, `mypy-extensions`, `pathspec`, `tomli`,
     `typing-extensions`. Markers appear on `librt`
     (`platform_python_implementation != 'PyPy'`) and `tomli`
     (`python_full_version < '3.11'`). Do not hand-edit the file; if a value
     looks wrong, fix the input and re-run `make lock`.
   - Add a header comment to `requirements-dev.txt` stating it is the input and
     that `requirements-dev.lock` is generated by `make lock` and is what CI and
     `make setup` install.

3. **A-033 checker + tests.**
   - `.github/scripts/check-dev-requirements-lock.py`, modeled on
     `.github/scripts/check-trellis-provenance.py`'s CLI shape: module docstring
     naming the gap it closes, `argparse` with `--repo`, findings printed as
     `<class>: <detail>`, exit 0/1/2, and a `CheckError` for environment/usage
     problems. Findings classes: `pin-missing` (direct pin absent from the
     lock), `pin-mismatch` (present at a different version), `unhashed` (a lock
     entry with no `--hash=`), `unpinned` (a lock entry not pinned with `==`),
     and `input-unpinned` (a requirement line in `requirements-dev.txt` that is
     not an `==` pin). The last class matters because a non-`==` line would
     otherwise fail the entry regex and be skipped silently — a loosened pin
     must be a finding, not a no-op.
   - Parse rules (deliberately narrow, per design "Data And Command
     Contracts"). **Entry detection must not require `==`** — otherwise an
     unpinned line is skipped rather than reported, and the `unpinned` and
     `input-unpinned` classes above can never fire:
     1. An entry starts at any line that is not blank, not a comment, and not
        indented — i.e. `^(?![ \t#])\S`. That is the *entry* rule.
     2. Its name and pin are then read with
        `^([A-Za-z0-9._-]+)\s*==\s*([^ ;\\]+)`. A **non-match is the finding**
        (`unpinned` in the lock, `input-unpinned` in `requirements-dev.txt`),
        never a skip.
     3. An entry owns the indented continuation lines that follow it, which is
        where `--hash=` values are looked for.

     Normalize distribution names per PEP 503 (lowercase, runs of `-_.`
     collapsed to `-`) so `PyYAML` matches `pyyaml`. The unit tests must include
     a lock fixture whose entry is `ruff>=0.16` and assert the checker exits 1
     with an `unpinned` finding — a skip would pass silently, which is the exact
     bug this rule exists to prevent.
   - `tests/test_dev_requirements_lock.py`: cover the passing repository state
     plus each finding class using `tempfile.TemporaryDirectory` fixtures
     (the isolation pattern the existing `tests/` modules use), and the exit-2
     path for a missing file. Every negative case builds its own fixture repo
     and passes `--repo <tmpdir>`; **no test mutates the real
     `requirements-dev.txt`**. Must keep `.github/scripts` coverage above the
     80% floor — check with `make test`, not by inspection.
   - **Register the new file in Trellis provenance before running the gate.**
     `check-trellis-provenance.py` enumerates tracked `.github` files with
     `git ls-files` (`:159`) and reports `uncovered:` for anything absent from
     the manifest (`:204`), so the new script fails `make trellis-provenance`,
     `make check`, and the CI `release-payload-gate` until absorbed:
     ```bash
     git add .github/scripts/check-dev-requirements-lock.py
     .venv/bin/python .github/scripts/check-trellis-provenance.py --write \
       --accept .github/scripts/check-dev-requirements-lock.py
     ```
     Note the ordering trap: because discovery is `git ls-files`-based, the gate
     passes while the file is untracked and starts failing only after `git add`.
     Commit the regenerated `.github/trellis-provenance.json` in the same PR.
     Editing existing `.github` files needs no regeneration — `tests.yml` and
     the sibling scripts are listed under `repoOwn`, which records paths, not
     hashes.

4. **A-033 consumer switch.** Order matters: the lock must exist and pass its
   own check before anything installs from it.
   - `Makefile:13-14` `setup` — **both lines change**:
     ```
     setup:
     	"$(PYTHON)" -m venv --clear "$(VENV)"
     	"$(VENV_PYTHON)" -m pip install --require-hashes --only-binary :all: -r requirements-dev.lock
     ```
     `--clear` is not cosmetic. `python -m venv` over an existing directory
     reuses it, so packages that dropped out of the lock survive and
     `make check` silently gates a superset of the locked set. Both install
     flags are likewise required — see design "Data And Command Contracts";
     hashes alone do not stop a source build.
   - New `lock-check` target running the checker with `$(RUN_PYTHON)`; append it
     to `check:` (`Makefile:56`).
   - `.sd-ai-command-pack/check.json`: add
     `{ "id": "repo.lockcheck", "argv": ["make", "lock-check"], "cwd": ".", "timeoutSeconds": 60 }`.
     It is guard-safe — read-only, writes nothing under sd-check's guarded paths.
   - `.github/workflows/tests.yml`: in all three jobs that install
     (`unittest` `:38-39`, `lint` `:59-60`, `release-payload-gate` `:79-80`),
     switch `cache-dependency-path` to `requirements-dev.lock` and the install to
     `python -m pip install --require-hashes --only-binary :all: -r requirements-dev.lock`.
     (`python` is correct *inside* the workflow — `actions/setup-python` puts it
     on `PATH` — but not in local shell commands, see step 1.)
     Add a `- run: python .github/scripts/check-dev-requirements-lock.py` step
     to the `lint` job, placed **before** the install step: the checker is
     stdlib-only, and a broken lock should fail with its own findings rather
     than with a pip hash error.
   - **Reinstall the local venv from the lock before gating.** `RUN_PYTHON`
     prefers the existing `.venv` (`Makefile:4-5`), which currently holds the
     pre-lock transitives (`ast_serialize==0.6.0`). Running `make check` against
     that venv would gate the *old* dependency set and prove nothing about the
     upgrade. So:
     ```bash
     make setup     # with --clear, rebuilds .venv from requirements-dev.lock
     make check     # now actually exercises the locked versions
     ```
     The first lock is an upgrade, not a freeze (design risk 8) —
     `ast-serialize` moves 0.6.0 → 0.8.0 under an unchanged `mypy==2.3.0` — so a
     lint or type regression it causes must surface here, in this PR. If
     `make setup` is skipped, say so instead of reporting the gate as green for
     the new pins.

## Validation Plan

Focused, in order:

```bash
bash -n scripts/update_repomix
.venv/bin/python -m unittest discover -s tests -p "test_repomix.py"
.venv/bin/python -m unittest discover -s tests -p "test_dev_requirements_lock.py"
make lock-check
```

Regeneration determinism (proves the committed lock is compiler output, needs
network):

```bash
before=$(mktemp) && cp requirements-dev.lock "$before" \
  && make lock && diff "$before" requirements-dev.lock && rm -f "$before"
```

Install contract in a throwaway venv. Use `mktemp -d`, not a fixed `/tmp` path:
a reused `/tmp/lockprobe` from an earlier run would install into a venv that
already has the packages, turning a real failure into a false pass.

```bash
set -euo pipefail
probe=$(mktemp -d)
trap 'rm -rf "$probe"' EXIT      # cleanup must not become the exit status:
                                 # `…; rm -rf` would report the removal, so a
                                 # failed install would read as a pass
python3 -m venv "$probe"
"$probe/bin/python" -m pip install --require-hashes --only-binary :all: \
  -r requirements-dev.lock
"$probe/bin/python" -m pip freeze
```

Negative test for the guard. It runs against a **disposable fixture**, never the
real `requirements-dev.txt`: step 2 adds a header comment to that file, and a
`git checkout` to undo a test mutation would silently discard it along with any
unrelated working-tree edit. It also asserts the exit code explicitly — chaining
`make lock-check; git checkout …` reports the checkout's status, so a checker
that wrongly *passed* would look identical to one that correctly failed.

```bash
set -uo pipefail
fixture=$(mktemp -d) || { echo "FAIL: mktemp -d failed"; exit 1; }
[ -n "$fixture" ] && [ -d "$fixture" ] || { echo "FAIL: no fixture dir"; exit 1; }
trap 'rm -rf "$fixture"' EXIT
cp requirements-dev.txt requirements-dev.lock "$fixture/"
python3 - "$fixture" <<'PY'
import pathlib, re, sys
root = sys.argv[1]
assert root and pathlib.Path(root).is_dir(), f"refusing to edit: bad fixture {root!r}"
p = pathlib.Path(root) / "requirements-dev.txt"
p.write_text(re.sub(r"^ruff==.*$", "ruff==0.0.1", p.read_text(), flags=re.M))
PY
.venv/bin/python .github/scripts/check-dev-requirements-lock.py --repo "$fixture"
status=$?
[ "$status" -eq 1 ] && echo "PASS: guard failed as required" \
  || { echo "FAIL: expected exit 1, got $status"; exit 1; }
```

The `mktemp` guard and the in-script `assert` are both load-bearing: an
unguarded `fixture=` that came back empty would make `--repo ""` and
`Path("") / "requirements-dev.txt"` resolve against the **repository working
directory**, so the "never mutates the real file" guarantee above would be false
exactly when `mktemp` failed. Note `set -e` is deliberately *not* used here —
the checker is expected to exit 1, and `-e` would abort before the assertion.

(`sed -i` is deliberately avoided — its in-place syntax differs between BSD and
GNU, and this repository's CI runs both macOS and ubuntu.)

Broad gate before pushing: `make check` (test, lint, release-check,
shell-syntax, trellis-provenance) plus the new `lock-check`.

`make repomix` is the only end-to-end check for A-034 and needs network plus
`npx`. Run it if available and confirm `docs/repomix-map.md` still generates; if
not available, report A-034 as statically verified (`bash -n` + unit test) and

## Review Notes

- The single most reviewable claim is the ownership split. Reviewers should
  re-run the two lookups from `quality-guidelines.md:772-784` against
  `.opencode/package.json` rather than trusting the design table.
- `--require-hashes --only-binary :all:` changes failure behavior for everyone
  running `make setup`; call it out in the PR body, including why hashes alone
  are not enough (a hashed sdist would still build from source).
- The `.github/trellis-provenance.json` diff is a required consequence of adding
  a `.github` file, not an unrelated change — say so, or a reviewer will ask.
- The lock is a large generated diff — a 2026-08-10 probe of the exact `make
  lock` command produced 494 lines for these 10 entries; expect that order of
  magnitude, not that exact number. Say so in the PR body so reviewers skip it
  deliberately rather than skim it.
- Dependabot PRs will now go red until the lock is regenerated. That is designed,
  documented, and the reviewer-visible cost of A-033.
- The checker's parser is intentionally narrow. If review pushes toward a full
  requirements-grammar parser, that is scope growth — the input is a file this
  repository generates itself.

## Rollback Points

1. After step 1 — A-034 is self-contained; reverting its three files
   (`scripts/update_repomix`, `tests/test_repomix.py`, `README.md`) loses
   nothing else.
2. After step 3 — lock and checker exist but nothing installs from them; the
   repository still builds exactly as before.
3. After step 4 — the risky step. Revert `Makefile`, `tests.yml`, and
   `check.json` to restore `requirements-dev.txt` installs. The lock can stay in
   the tree harmlessly, but the `requirements-dev.txt` header comment added in
   step 2 must be reverted with them: it asserts that CI and `make setup`
   install the lock, which stops being true the moment the consumers roll back.
   Leaving it is a documentation lie that survives the rollback.
4. Step 5 is documentation only.
