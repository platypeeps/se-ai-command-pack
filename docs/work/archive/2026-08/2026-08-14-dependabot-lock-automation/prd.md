# Automate requirements-dev.lock regeneration for Dependabot PRs

## Goal

Let a Dependabot pip PR reach green without a maintainer manually running
`make lock`, so the `sd-update-deps` auto-merge class stops being structurally
empty for this repository.

## Background

Nothing installs from `requirements-dev.txt`. `make lock` compiles it into
`requirements-dev.lock` (pinned, hashed, wheel-only), and CI and `make setup`
install from the lock with `--require-hashes --only-binary :all:`. Dependabot
bumps the input file only, so `check-dev-requirements-lock.py` fails every bot
PR with `pin-mismatch: ... run make lock`.

This is documented behaviour, not a regression (CONTRIBUTING.md, "Lock
regeneration"). The cost is that every bot pip PR needs a maintainer commit
before it can go green, and `sd-update-deps` is forbidden from editing
lockfiles or pushing to bot branches — so its auto-merge class can never
contain a pip PR here.

Observed on 2026-08-14 with #221 (coverage) and #222 (ruff): both red on the
same gate, both superseded by maintainer PR #223, which also grouped patch and
minor pip updates into one weekly PR. Grouping reduced the frequency of the
manual step; it did not remove it. This task removes it.

## Constraints

- The lock must keep its current guarantees: fully pinned, hashed, wheel-only,
  generated by `make lock` (`uv pip compile --universal --python-version 3.10
  --generate-hashes --no-header --only-binary :all:`). No weakening of
  `--require-hashes` installs to make automation easier.
- `check-dev-requirements-lock.py` must remain an enforcing gate on every PR.
  Automation regenerates the lock; it does not suppress the check.
- Do not weaken the `sd-update-deps` contract. That skill must remain unable to
  edit lockfiles or push to bot branches; the automation lives in CI, not in
  the skill.
- Majors stay ungrouped and manual, per the current `.github/dependabot.yml`.

## Security constraint (primary design driver)

Workflows triggered by Dependabot receive a read-only `GITHUB_TOKEN` and no
access to secrets. Pushing a regenerated lock back to the bot branch therefore
requires an elevated credential — `pull_request_target`, a GitHub App token, or
a PAT.

The hazard is specific: the job would hold a writable credential while running
`make lock`, which executes `uv` against a manifest whose contents came from a
bot branch. Any design must state explicitly:

- which trigger is used and why;
- what the credential can write to, and how that is scoped down;
- what repository content the job executes, and from which ref it is checked
  out (base ref vs head ref is the crux);
- how a malicious or compromised branch is prevented from escalating into a
  write against protected refs.

A design that does not answer these is not acceptable, regardless of whether it
works.

## Requirements

- A Dependabot pip PR that bumps a pin in `requirements-dev.txt` ends with a
  matching `requirements-dev.lock` on the same PR, without maintainer action.
- The regenerated lock is byte-identical to what a maintainer running
  `make lock` locally at the same pins would produce.
- The lock-parity gate still fails a PR whose lock does not match its input.
- The automation is inert for non-Dependabot PRs.
- The credential model is documented in CONTRIBUTING.md alongside the existing
  "Lock regeneration" section, which must be updated — it currently instructs
  the maintainer to do this by hand.

## Acceptance criteria

- [ ] A real or simulated Dependabot pip bump reaches all-green with no human
      commit on the branch.
- [ ] `make lock-check` passes on that PR, and still fails on a deliberately
      mismatched lock (negative case exercised, not assumed).
- [ ] The lock produced by CI matches a locally produced lock for the same
      pins, verified by diff.
- [ ] The workflow does not run, or cannot write, for a PR from a
      non-Dependabot actor — verified, not asserted.
- [ ] `design.md` answers every question in "Security constraint" above.
- [ ] CONTRIBUTING.md no longer tells maintainers to run `make lock` by hand
      for bot PRs, and describes the credential model instead.

## Open questions

- `pull_request_target` + checkout of the base ref, versus a GitHub App token,
  versus a `workflow_run` follow-up job: which gives the smallest write scope?
- Can regeneration run against the base ref's `Makefile` and workflow
  definition while reading only the head ref's `requirements-dev.txt`? That
  would remove bot-branch code execution from the writable job entirely, and is
  the most promising direction.
- Is `uv` version drift between CI and maintainer machines a source of lock
  churn? If so, pin `uv` too.

## Non-goals

- npm. The root `package.json` declares no dependencies, and
  `.opencode/package.json` is upstream-Trellis vendored (see the existing
  out-of-scope note in CONTRIBUTING.md).
- Changing what the lock guarantees, or how the runtime installs it.
- Auto-merging majors.
